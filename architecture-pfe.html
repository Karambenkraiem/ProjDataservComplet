1. Introduction et Présentation du Projet

DataServ est une application web de gestion du service technique développée dans le cadre d'un projet de fin d'études. Elle permet à une entreprise de gérer l'ensemble de son cycle d'intervention : ouverture de tickets, assignation de techniciens, suivi des interventions, génération de rapports et facturation des heures contractuelles.

Rôles utilisateurs

RôleResponsabilités
MANAGERGestion globale : clients, techniciens, tickets, rapports, tableaux de bord, activation/désactivation des comptes
TECHNICIENConsultation des tickets assignés, mise à jour du statut, enregistrement des interventions
CLIENTSoumission de tickets, suivi des interventions, consultation du solde de contrat

4. Architecture Backend (NestJS)

Le backend suit l'architecture modulaire de NestJS. Chaque domaine métier est encapsulé dans un module indépendant avec son contrôleur, service, DTOs et dépendances propres.

Structure des modules

│   ├── auth.service.ts
│   ├── jwt.strategy.ts
│   └── dto/auth.dto.ts
├── users/              # Gestion des utilisateurs

├── tickets/            # Tickets d'intervention
├── interventions/      # Détails des interventions
├── techniciens/        # Rendement & statistiques techniciens

Chaîne de traitement d'une requête

Requête HTTP → Nginx → JwtAuthGuard (validation token + isActive) → RolesGuard (vérification MANAGER/TECHNICIEN/CLIENT) → Pipe (validation DTO) → Controller → Service → PrismaService → PostgreSQL

Système de guards et sécurité

  • JwtAuthGuard : vérifie la validité du token JWT ET que l'utilisateur est actif (isActive = true). Un compte désactivé reçoit une 401 immédiate.
  • RolesGuard : vérifie le rôle de l'utilisateur via le décorateur @Roles().
  • @Public() : décorateur qui exclut une route de l'authentification (ex. : /auth/login).

Le frontend utilise l'App Router de Next.js avec rendu côté serveur (SSR) et protection des routes par rôle. La gestion d'état est assurée par Zustand pour l'authentification et TanStack Query pour le cache des données serveur.

Gestion de l'état

OutilUsagePersistance
Zustand Token JWT, profil utilisateur, état d'authentification localStorage (dataserv-auth)
TanStack Query Cache des données serveur (tickets, clients, users) Mémoire (TTL configurable)

Client HTTP (Axios)

Le fichier api.ts centralise toutes les communications avec le backend :

  • Intercepteur requête : injecte automatiquement le token JWT depuis le localStorage.
  • Intercepteur réponse 401 : déconnecte l'utilisateur et redirige vers /auth/login. Si l'erreur indique "désactivé", redirige avec ?disabled=1 pour afficher le message approprié. Exception : l'endpoint /auth/verify-password gère ses propres tentatives (3 max) avant déconnexion.

Flux d'authentification

Connexion : Login form → POST /auth/login → JWT token → Zustand store → redirect selon rôle

Navigation : layout.tsx (guard) → vérifie isAuthenticated + rôle → redirect si non autorisé

Compte désactivé : JWT strategy retourne 401 → intercepteur détecte "désactivé" → logout → /auth/login?disabled=1 → bannière orange

8. Sécurité

MécanismeImplémentationDétail
Authentification JWT (JSON Web Token) Token signé avec secret configurable, expiration 24h. Refresh token 7 jours.
Hachage des mots de passe bcryptjs (salt=12) Aucun mot de passe stocké en clair. Comparaison via bcrypt.compare().
Autorisation RBAC (Role-Based Access Control) Chaque endpoint protégé par @Roles(). RolesGuard vérifie après JWT.
Désactivation de compte Champ isActive JWT strategy vérifie isActive à chaque requête. Compte désactivé → 401 immédiat.
Suppression sécurisée Vérification mot de passe manager Suppression d'un client requiert le mot de passe du manager. 3 tentatives max avant déconnexion.
Protection des données Sélection explicite des champs Le champ password est toujours exclu des réponses API via select Prisma.
Protection HTTP Helmet.js Headers de sécurité HTTP (CSP, HSTS, XSS protection).
Rate limiting @nestjs/throttler Protection contre les attaques par force brute sur les endpoints.

10. Flux de Données Principaux

Flux 1 — Connexion d'un utilisateur

1. Utilisateur saisit email + mot de passe dans /auth/login
2. Frontend POST /api/v1/auth/login via Axios
3. Nginx route vers backend :3001
4. AuthService : findUnique(email) → bcrypt.compare() → vérification isActive
5. Génération JWT (accessToken 24h + refreshToken 7j)
6. Réponse : token + profil utilisateur
7. Zustand stocke token dans localStorage
8. Redirect vers le dashboard selon le rôle

Flux 2 — Création d'un ticket

1. Manager remplit le formulaire de ticket
2. POST /api/v1/tickets avec Bearer token
3. JwtAuthGuard valide le token et vérifie isActive
4. RolesGuard valide le rôle MANAGER
5. TicketsService crée le ticket avec createdById injecté
6. TanStack Query invalide le cache ['tickets']
7. La liste se rafraîchit automatiquement

Flux 3 — Suppression sécurisée d'un client

1. Manager clique "Supprimer" → dialog de confirmation s'ouvre
2. Saisie du mot de passe (3 tentatives maximum)
3. POST /api/v1/auth/verify-password avec le mot de passe saisi
4. Si 401 (mot de passe incorrect) : compteur incrémenté. À 3 tentatives → logout immédiat
5. Si 200 (correct) : DELETE /api/v1/users/:id (cascade supprime aussi le client et ses tickets)
6. Cache invalidé → liste rechargée

Flux 4 — Désactivation d'un compte en session active

1. Manager désactive un compte (PATCH /api/v1/users/:id/deactivate)
2. L'utilisateur désactivé effectue une nouvelle requête
3. JwtStrategy vérifie isActive → false → throw UnauthorizedException
4. Intercepteur Axios reçoit 401 avec message "désactivé"
5. localStorage vidé + redirect /auth/login?disabled=1
6. Page login affiche bannière orange : "Compte désactivé — contacter DataServ"
